An accessible benefits portal, built end to end

This project is a code sample for a Senior .NET Developer / Front-End UI/UX role. It shows the same person building the back end and the interface people would actually see: ASP.NET Core 8 APIs and services, SQL Server data access, a reusable design system in SCSS, and WCAG 2.1 AA-first front-end engineering.

Try the complete journey: submit a demo application, get a reference number, then check its status. Or start from the seeded demo records, for example reference IA-DEMO-2026-000101.

What this demonstrates

.NET and C# — about 40% of the role

Clean, layered ASP.NET Core 8 code: controllers, services, repositories, dependency injection, DataAnnotations plus business-rule validation, global exception handling, security headers and structured logging. See src/IowaBenefitsPortal/.

Front-end, UI and UX — about 40% of the role

Semantic HTML5, SCSS design tokens, responsive layouts, validated forms with error recovery, and a live design-system page. No framework is required to run the demo; the components are framework-agnostic, and Angular experience is evidenced on the resume rather than faked here.

Middleware and APIs — about 10%

Versioned REST endpoints (/api/v1/…, with unversioned aliases), a /health endpoint, and three documented middleware components. See the API contract in the README.

SQL Server — about 10%

Schema, fictional seed data, parameterized queries and a stored procedure in database/sql/, plus a repository implementation that is only used when a connection string is supplied by environment configuration.

Accessibility first, not an afterthought

Every page uses landmarks, one h1, a logical heading order, a skip link, visible focus, real <label> elements, error summaries linked to fields, and an aria-live status region. The remediation focus matches the revised resume: missing labels, keyboard interaction, focus order, and dynamic-content accessibility. Status is shown with icon and text, never colour alone. The full checklist, axe and JAWS workflow, and before/after remediation examples are in docs/ACCESSIBILITY.md.

Honest limit: an automated check reporting no violations does not make a page compliant. Manual keyboard and JAWS testing are still required, and no compliance or certification is claimed for this demo.

Architecture at a glance

Browser pages (HTML, CSS, JavaScript) call the ASP.NET Core API, which validates, runs the fictional eligibility rule, and stores the result through a repository interface. The default store is in-memory; SQL Server is a drop-in replacement. See the Mermaid diagram in the README and docs/ARCHITECTURE.md.

Browser (wwwroot) → Controllers → ApplicationService → EligibilityService
                                        ↓
                              IApplicationRepository → In-memory (default)
                                                         or SQL Server (configured)
