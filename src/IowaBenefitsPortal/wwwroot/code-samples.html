Code samples

Healthcare — dashboard + FHIR pattern

code-samples/csharp/HealthcareDashboard.cs — capacity summary, SignalR-style live update shape, FHIR R4 patient summary mapping (name, identifiers redacted in samples), and an AI-summary request that requires human review before display. No PHI, no real patient data.

Banking — loan API pattern

code-samples/csharp/LoanApi.cs — intake DTO with validation, idempotency key handling, underwriting state machine (Received → UnderReview → Approved/Declined), and an event payload for Kafka/MSK. No real applicant data.

Airline — reservation pattern

code-samples/csharp/FlightReservation.cs — fare search result, reservation hold with expiry, itinerary change/cancellation rules, and an idempotent nightly load record.

Support — ticket pattern

code-samples/csharp/SupportTicket.cs — ticket creation, assignment, SLA deadline calculation, escalation, and audit history. Plus the legacy Web Forms sample and modern equivalent in code-samples/legacy/.

C# / .NET — runnable core

  • src/IowaBenefitsPortal/Controllers/ — versioned REST API, validation, 201/400/404 handling
  • src/IowaBenefitsPortal/Services/ — application + fictional eligibility rules, cleanly separated from HTTP
  • src/IowaBenefitsPortal/Models/, Dtos/ — stored shapes and DataAnnotations-validated request contracts
  • Dependency injection in Program.cs: services and the repository interface are registered once and swapped by configuration (in-memory by default, SQL Server when a connection string is set)

REST APIs and middleware

  • src/IowaBenefitsPortal/Middleware/ — global exception handling (generic error shape, no stack traces or personal data leaked), security headers, and request logging without bodies or personal data
  • API contract, versioned routes (/api/ and /api/v1/), and GET /health are documented in docs/ARCHITECTURE.md

SQL Server

  • database/sql/01_schema.sql — tables and constraints for services and applications
  • database/sql/02_seed_fictional.sql — fictional seeded records only, including the demo references used by the status page
  • database/sql/03_queries.sql — parameterised queries and a stored procedure; the SQL repository in Repositories/ uses parameterised ADO.NET, not string-built SQL
  • Production connection guidance (environment variables, Key Vault / Secrets Manager, never in source) is in docs/SQL_SERVER.md and docs/SECURITY_AND_CONFIG.md. No live SQL Server run was available in this build environment, so the scripts are not claimed to have been executed against a live server.

HTML5 and JavaScript

  • wwwroot/apply.html + js/apply.js — the complete journey: entry, client-side validation, error summary with focus, error recovery, submission, and confirmation reference
  • wwwroot/status.html + js/status.js — look up a reference and announce the result in a live region
  • wwwroot/services.html + js/services.js — catalogue loaded from the API, with a loading and error state
  • All pages use semantic landmarks, one h1, real labels, and native controls (dialog, checkboxes) rather than custom mouse-only widgets

Sass / SCSS

  • frontend/scss/_tokens.scss — design tokens as variables and maps (colours, type, spacing, breakpoints)
  • frontend/scss/_mixins.scss — focus-ring, respond-to, button, card mixins with parameters
  • frontend/scss/_base.scss, _components.scss, main.scss — element defaults and reusable components; nesting is kept to one level for states only, no deep nesting, @extend chains, or !important
  • The compiled CSS in wwwroot/css/main.css is checked in, so the demo runs with no Sass build step; rebuild it with npx sass frontend/scss/main.scss src/IowaBenefitsPortal/wwwroot/css/main.css

Reusable UI components

Live on the design-system page: buttons, links, form controls, alerts, navigation, cards, tables, dialogs, and error/success states, all built from the same tokens. The difference between a design system, a component library, and a CSS framework — and how a team adopts an organisation-wide system without rewriting every page — is documented in docs/DESIGN_SYSTEM.md.

Accessibility remediation — before / after

Worked examples in docs/ACCESSIBILITY.md: missing labels, unannounced validation errors, skipped heading levels, keyboard traps, inadequate contrast, and missing accessible names — each shown broken, then fixed. The manual axe and JAWS workflow, keyboard checklist, focus-management checks, contrast and reflow checks, and the honest limit (a clean automated run is not a compliance claim) are in the same document. No accessibility certification is claimed.

Automated tests

  • tests/IowaBenefitsPortal.Tests/PortalTests.cs — eligibility rules (eligible, likely eligible, needs review, unknown service), API success (201 with reference), validation failures (bad ZIP, no consent, unknown service → 400), not-found (404), seeded-record lookup, and HTML accessibility smoke tests (skip link, landmarks, single h1, labels, no placeholder-only labels)
  • Run them with dotnet test IowaBenefitsPortal.sln. Test status in this environment is reported honestly in the README; do not claim a pass that has not been observed.

Azure DevOps CI / CD

  • azure-pipelines.yml — restore → format check → build → test → accessibility smoke tests → publish artifact
  • .github/workflows/ci.yml — the same stages for GitHub Actions; see docs/CI_CD.md for the AWS future path (CodePipeline / CodeBuild / ECS sketch, no cloud resources created)

Legacy modernisation

code-samples/legacy/ — a Web Forms benefits-lookup sample (page, code-behind, user control) plus its modern ASP.NET Core equivalent, and docs/LEGACY_MODERNIZATION.md explaining when Web Forms maintenance is appropriate and when migration is the right call. The legacy files are illustrative and are not compiled in the .NET 8 project.
